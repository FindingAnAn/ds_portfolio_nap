Flagship Case Study - Vietnam Post

A production-oriented churn warning system for B2B customers

An end-to-end batch machine learning system that converts monthly transaction data and limited confirmed churn labels into a precision-focused retention list. The system covers ingestion, leakage-safe temporal features, weak supervision, model governance, scoring, monitoring, and Kubernetes-based orchestration.

01 - Problem Framing

From a probability model to a usable retention decision

The business question was not simply, "Can churn be classified?" The operational question was: which active B2B customers should the customer-care team contact first, before a likely service stop occurs? A useful system therefore had to optimize the complete decision chain: reliable data, early warning, a manageable list, understandable reasons, repeatable execution, and evidence that the model remained healthy over time.

Business Constraints
  • Outreach capacity is limited; a long alert list has low practical value.
  • Confirmed churn labels are sparse, delayed, and incomplete.
  • Customer behavior changes over time, so random validation is misleading.
  • Every warning must be traceable to its data window and model decision.
System Objective
  • Score currently active customers for churn within the next two months.
  • Favor precision when selecting customers for intervention.
  • Cap the action list using a dynamic percentile threshold.
  • Keep a previous accepted model available when a new candidate regresses.
Success is defined at the workflow level. The deliverable is a governed PostgreSQL action table, not an isolated notebook or a one-time accuracy score.

02 - Target And Time Contract

A strict definition of churn and what the model is allowed to know

For an observation month T, features are computed only from information available through the feature window end. The target then looks forward over H = 2 months. A customer is labeled churned when both item count and revenue are zero throughout that future horizon; any item activity or positive revenue keeps the target active.

y = 1 when item_count = 0 AND total_fee = 0 for every month in [T+1, T+H]; otherwise y = 0.

This temporal contract appears throughout ingestion, feature construction, training-set creation, evaluation, scoring metadata, and backtesting. Lifetime features are also rebuilt "as of" each historical window, preventing future transactions from leaking into past examples.

03 - System Architecture

Five Airflow DAGs with separated operational responsibilities

The repository is organized as a Python modular monolith under src/. Airflow handles orchestration, while computational jobs run in isolated Kubernetes pods. PostgreSQL is both the analytical backbone and the system of record for source data, engineered features, model configuration, predictions, and model-quality monitoring.

01ingest_data

Scans incoming ZIP files, validates CSV structure, loads source tables, and records success or failure.

02build_features

Builds lifetime and sliding-window features after a successful ingestion run.

03generate_eda_reports

Produces missingness, outlier, correlation, class-balance, and temporal-drift evidence.

04run_churn_pipeline

Prepares datasets, trains, evaluates, governs, scores, explains, and exports predictions.

05clean_runtime_files

Applies retention policies to bundles, logs, processed files, failed files, and incoming data.

04 - Feature Engineering

Sixty-six modeled variables across behavior, value, quality, and trend

The feature engine combines all-time customer context with rolling 1-6 month behavior windows. PostgreSQL SQL is the default engine for deterministic aggregation; PySpark can be enabled for lifetime-as-of processing when volume requires distributed execution. Window size is not treated as a fixed assumption: the dataset pipeline searches for W* using walk-forward logic.

EWMA signalssmoothed level and short-term delta for seven signals
EWMA_t = alpha * X_t + (1 - alpha) * EWMA_(t-1), with default alpha = 0.3.
Delta_EWMA = latest smoothed signal - previous smoothed signal.

EWMA is applied to item volume, revenue, complaints, delays, incomplete orders, order count, and satisfaction. The paired delta captures acceleration or deterioration that a simple aggregate can miss. Feature sanity checks reject NaN output and columns whose names indicate target or future leakage.

05 - Learning With Limited Labels

Conservative weak supervision instead of pretending unlabeled means negative

Confirmed churn files from customer care provide strong positive evidence, but they do not cover every real churn event. Treating every remaining customer as a true negative would introduce systematic label noise. The dataset pipeline therefore separates four evidence levels.

GroupConstructionTraining treatment
Confirmed churnExplicit CSKH confirmationTarget 1.00, full sample weight
Pseudo churnClose to churn prototype plus downward trendSoft target 0.90, PU-derived weight
Reliable negativeStrong recent activityTarget 0.00, full sample weight
PU unlabeledInsufficient evidence either waySoft target and reduced confidence weight

A leading churn prototype is estimated from confirmed churners before the outcome window. The system uses a regularized covariance matrix and Mahalanobis distance, which accounts for correlation and scale among features rather than relying on raw Euclidean distance.

D_M(x) = sqrt((x - mu)^T * Sigma^-1 * (x - mu))

Similarity to the prototype is combined with a downward behavior signal before assigning a pseudo positive. A cached prototype may be reused for up to a configured age when a new confirmation file is unavailable, and that fallback is recorded rather than silently changing the training logic.

06 - Validation Design

Time-aware evaluation and explicit leakage controls

Churn is a temporal problem, so a random row split can let the model learn from a future regime and overstate real performance. This system uses walk-forward windows, a minimum number of historical training periods, a held-out portion of confirmed churners, and scaling fitted only on training rows.

1

Observation cutoffDetect the latest usable month and move the feature window back before label construction.

2

Scope as of cutoffApply account age, lifetime order, and inactivity criteria without using later activity.

3

Walk-forward W* searchEvaluate candidate history lengths using ordered monthly folds.

4

Label isolationSplit confirmed churn IDs before prototype creation and evaluation.

5

Train-only preprocessingFit scaling statistics on training data, then transform evaluation and prediction data.

6

Matured backtestMeasure precision-in-list only after the two-month future window becomes observable.

The system stores window_end, w_star, horizon, and the effective threshold with its output so a prediction list can be reconstructed and audited.

07 - Modeling And Governance

XGBoost is only one component; the acceptance gate is the control system

XGBoost is used for nonlinear tabular interactions, missing-value tolerance, regularization, and efficient weighted learning. The model is trained with sample weights from the limited-label strategy and early stopping. Evaluation emphasizes precision because unnecessary outreach consumes operational capacity.

Performance is intentionally not presented as one permanent accuracy number. Each run can accept or reject a candidate; authoritative metrics live in bundle metadata and PostgreSQL. This avoids turning a historical benchmark into a misleading production claim.

08 - Operational Output

A capacity-aware action list with traceable reason signals

All eligible active customers receive a churn probability. The final effective threshold is the stricter of the evaluation-selected threshold and the dynamic 90th-percentile cutoff. This makes the top 10% a maximum list-size target: if the model threshold is stricter, fewer customers are flagged.

In the current implementation, reason fields are generated from the model's gain-based global feature importance and each customer's position relative to the population median. This is a lightweight operational explanation, not a claim of causal attribution or full local SHAP explanation.

09 - Monitoring And Reliability

Separate model-quality evidence from infrastructure telemetry

The design uses two observability planes. PostgreSQL records the statistical and decision behavior of the model, while Prometheus and Grafana monitor the infrastructure that executes it. This separation makes incident diagnosis clearer: a healthy pod does not imply a healthy model, and stable scores do not imply sufficient compute resources.

Model Quality - PostgreSQL
  • run_log: status, acceptance, retraining, scoring, and notes.
  • score_drift: score quantiles, list size, and risk ratio.
  • feature_drift: PSI and discrete KS by feature.
  • backtest: precision-in-list after the label horizon closes.
Platform Health - Prometheus/Grafana
  • Kubernetes pod states and pending/failed jobs.
  • CPU and memory consumption by pipeline pod.
  • Scheduler and container restart rates.
  • Node disk pressure and resource capacity.

Housekeeping runs independently and enforces retention for model bundles, Airflow logs, processed inputs, failed inputs, and unprocessed incoming files. Failed source files are preserved in a dedicated path to support diagnosis and retry.

10 - Engineering Quality

Configuration, tests, documentation, and reproducible artifacts

Production behavior is controlled through typed configuration and environment variables rather than hard-coded credentials or machine-specific paths. Database secrets are injected through Kubernetes Secrets. Accepted bundles preserve the information needed to reproduce scoring and establish future drift baselines.

12 - Limits And Next Steps

What the current system does not claim

A scientifically credible case study should state uncertainty. The system is a batch prioritization tool, not a causal model and not a real-time API. Confirmed outcomes are incomplete, explanation fields are feature-based heuristics, and a precision metric cannot by itself prove business lift.

Current limitationPlanned improvement
Partial and delayed churn labelsFormalize label coverage measurement and active-learning feedback from CSKH.
Global gain-based reason signalsAdd validated local SHAP explanations with stability and usability checks.
Offline metrics do not measure retention liftRun controlled outreach experiments and measure incremental retained value.
Fixed contact-capacity policyOptimize thresholds by campaign capacity, expected value, and intervention cost.
Batch-only consumptionAdd a governed service layer only if a real-time business requirement emerges.
Potential segment variationAudit performance by customer tier, revenue band, service mix, and geography.
