Version 1 — Docker Compose + Airflow

1. System Goal

The system turns monthly VNPost customer and transaction data into an operational churn risk list. The output is designed for customer-care action: who is risky, how risky they are, and which behavioral signals explain the score.

  • Score active customers on a 2-month churn horizon.
  • Export high-risk customers into PostgreSQL and CSV-compatible tables.
  • Attach reason signals from SHAP where possible, with rule-based fallback when explanation artifacts are unavailable.

2. Airflow Chain

01IngestSaturday 05:00 ZIP scan and load.
02ValidateRun ingest validation before downstream trigger.
03FeaturesBuild lifetime and sliding-window tables.
04ModelMonthly XGBoost pipeline — horizon 2.
05MonitorRun logs, score drift, PSI/KS, backtests.

Real DAG chain: ds_churn_ingest → ds_churn_features → ds_churn_model_monthly. Model DAG runs python modeling/main.py run-monthly --horizon 2 --risk-threshold-pct 95.

3. ZIP Ingestion Design

Built around controlled full-refresh loads instead of ad hoc file appends — making repeated monthly uploads auditable and recoverable.

Data controls
  • Unzip and discover source CSV files.
  • Validate expected headers and table schema.
  • PostgreSQL COPY after transformation.
  • Track loads in ingest.ingest_log.
Failure handling
  • Copy failed ZIPs to failed-data storage.
  • Preserve original input, never delete.
  • Structured status: rows, skip reason, success, error.
  • Post-ingest maintenance without failing the whole job.

4. Feature Generation

Static lifetime metrics and dynamic K-month behavior windows in PostgreSQL. The key v1 engineering win is the smart recomputation strategy for sliding windows.

Before540+table computations
After18–20latest windows
Time45→8 mbenchmark
Reduction96%less redundant work
  • Existing stable windows are kept; only new and incomplete windows are recomputed.
  • Window table names generated dynamically from month ranges and K values.
  • Checkpoint and batch-insert logic reduce restart cost for long SQL jobs.

5. Monthly Modeling Pipeline

Sweeps candidate lookback windows, compares against the previous accepted model, retrains only when the candidate passes acceptance logic, and always scores active customers with the best available bundle.

StepImplementation detailPortfolio meaning
Sweep KFind best window candidateModel selection is part of the pipeline
Accept / rejectCompare candidate F1 against accepted bundlePrevents weak replacement models
ScoreExport risk list at threshold percentileProduces retention-ready customer list
BacktestPrecision-in-list monitoringChecks high-risk list remains useful

6. Monitoring Tables (v1)

V1 already includes a production-monitoring layer in PostgreSQL, focused on model output quality rather than UI dashboards.

Run-level tables
  • ml_monitor.run_log — status, accepted flag, notes.
  • score_drift — active count, risk count, quantiles, risk-ratio anomalies.
Quality checks
  • feature_drift — PSI and discrete KS per feature vs. training profile.
  • backtest — precision-in-list when future label windows become available.

Version 2 — Kubernetes · KubernetesPodOperator · Prometheus

7. What v2 Fixes

V1 had the core ML workflow. V2 raises the engineering bar: heavy jobs run in isolated Kubernetes pods, code is packaged as a modular monolith, monitoring splits between model-quality PostgreSQL tables and infrastructure metrics via Prometheus/Grafana.

  • Airflow uses KubernetesPodOperator for feature, EDA, and monthly model tasks.
  • Local deployment: kind, Helm values, Docker images, Kubernetes secrets, host-mounted churn data.
  • Accepted model bundle stores metrics, threshold, feature names, feature importance, model config, pipeline config.

8. DAG Architecture (v2)

01IngestScan ZIP files, validate, load source tables, emit XCom status.
02FeaturesBuild lifetime and 1–6 month sliding-window SQL tables.
03EDAGenerate missing, outlier, correlation, class balance, and drift reports.
04PipelineDataset prep, train, evaluate, accept/reject, score, export.
05HousekeepClean old bundles, logs, saved files, failed files, incoming files.

9. Dataset Preparation

The core intellectual part of v2. Handles limited churn labels by combining business scope rules, temporal validation, prototype similarity, PU-style weighting, and label smoothing.

Temporal logic
  • 2-month prediction horizon.
  • Walk-forward window selection with minimum train windows.
  • Active and at-risk tiers using recency thresholds.
  • Train-only scaling to avoid leakage.
Label logic
  • Confirmed churners from CSKH files.
  • Reliable negatives from recent active customers.
  • Prototype-based pseudo churn via Mahalanobis similarity.
  • Sample weights and soft labels for uncertain groups.
